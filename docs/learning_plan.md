## 组合与完成标准

- 用户确认在当前 RAG 外再做一个 Agent 项目；主项目由独立掌握程度、实际问题深度、验证证据和演示质量决定，不提前按技术名词指定。
- RAG 聚焦真实资料检索、证据追踪和一种有失败分析依据的改进；Agent 聚焦工具选择、参数校验、状态流转、终止条件与失败处理。
- 不保证项目带来面试或录用。编程、算法、模型基础和岗位实习时长要求单独准备；具体 JD 到投递阶段重新核实。

## RAG 阶段（当前主线）

1. 固定版本真实语料：采用 FastAPI 官方英文教程，首批六篇验证导入，后续按场景扩到约15–20篇；数量不是硬门槛。保留原样例。记录来源、版本、文件校验值及许可证。
2. 文档完整性与切块：检查标题、长段落、代码围栏及外部代码引用。原始 Markdown 不是渲染后的完整网页；不把缺失示例代码默认为已入库。根据观察补最必要的处理，再冻结基线。
3. 用真实开发问题定位一类失败，复用现有评测入口；只选择一项针对性改进（切块、召回或重排），记录效果与耗时代价。新场景另建并冻结开发/测试划分，旧题集保留，独立测试不参与调参。
4. 在干净环境按说明复现，完成演示与已知限制清单；Docker按交付需要选用。用户完成至少一次只给需求和验收标准的独立修改。
5. 收束标准：能够讲清场景、基线、失败、选择、验证和限制；能独立定位及修改小需求。暂缓失败耗时日志、界面美化和额外评测脚本。

## Agent 阶段（RAG 达到收束标准后）

- 初步方向：技术支持助手，两个只读工具起步（资料检索、虚构工单状态查询），不接真实企业账户。
- 依次完成工具调用协议、参数校验、结果回传、最大步数、错误出口及成本约束；对成功、工具失败和无法完成的路径做必要验证。
- 工单数据明确标为模拟；复用RAG能力但在独立项目中展示Agent的决策与执行链路。暂不堆多Agent、复杂记忆或平台功能。
